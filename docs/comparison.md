# Choosing a focus library for a TV app

[العربية](ar/comparison.md) · [Documentation](README.md)

## Where Itar earns its place

Consider an Android TV catalogue. A viewer opens a film from *Watch again*. The same film also appears in *Featured*. While Details is open, *Watch again* refreshes, and the view that used to show the film now displays another title. When the viewer presses Back, the app needs to return to the right copy of the film. Selecting the old position or focusing the recycled view could open a different title on the next press of Select.

**Evaluate Itar when your app needs to know which card actually received native focus as the catalogue changes.** Give each appearance a stable occurrence key and save the key that opened Details. When the collection is ready, request that occurrence. The Android adapter reports `applied` when the host confirms input focus on the matching target. If the title disappeared, the app can handle an `unavailable` outcome and choose where the viewer should go. If the viewer leaves during the request, the app can cancel it. A late host callback can still update the observed focus without turning a cancelled request into a success. [Route restoration and outcomes](guides/integration.md) · [Tests for late callbacks](../core/tests/transaction_cancel.cpp)

There is also a reason to try Itar on a screen where every card is already visible. On Android TV, supported remote moves between mounted cards and their focus highlights run on the native side. A busy JavaScript frame can delay a React update while the host continues to handle those moves. On tvOS, UIKit owns ordinary mounted navigation. Bringing an offscreen React cell into view can still require JavaScript. The C++ policy and request tests run on a development machine, so you can reproduce callback ordering before testing the same journey on a TV. [Who owns a move](guides/architecture.md#who-owns-a-move) · [Focus outcome tests](../core/tests/transaction_outcome.cpp)

## Where the alternatives fit

| What you are shipping | Where to start |
| --- | --- |
| A React app in a TV browser | **Norigin Spatial Navigation** offers the clearest starting point of these three. Its hooks attach to existing elements, its visual debugger shows why a candidate won, and its maintainers report production use on Samsung Tizen and LG webOS. It also offers React Native TV bindings. Itar’s DOM/Wasm adapter ships inside the example, and its Tizen and webOS builds still need physical-device validation. [Norigin’s platform matrix](https://github.com/NoriginMedia/Norigin-Spatial-Navigation#supported-devices) · [Norigin’s visual debugger](https://github.com/NoriginMedia/Norigin-Spatial-Navigation/blob/main/docs/guides/distance-calculation.md) · [Itar’s web TV guide](devices/web-tv.md) |
| One React navigation tree for native TV and web | **BAM’s React TV Space Navigation** lets a team express rows, grids and scrolling with components and use LRUD to navigate that tree across platforms. Its virtualized list exposes `focus(index)`. If you save a stable entry ID, you can look up its new index after a reorder and ask the list to focus it. The maintainers flag a limitation for catalogues with hundreds of virtualized rows. [BAM’s design and current limits](https://github.com/bamlab/react-tv-space-navigation) · [BAM’s virtualized list API](https://github.com/bamlab/react-tv-space-navigation/blob/main/docs/api.md#spatialnavigationvirtualizedlist) |

All three can identify a card. Norigin supports an explicit `focusKey`, a registration check and an asynchronous `setFocus`. BAM gives the app a list-level focus operation. Itar exposes the lifetime of a native focus request and its outcome as part of the React API. How much the application needs to know about that move is a useful way to choose. [Norigin’s focus service](https://github.com/NoriginMedia/Norigin-Spatial-Navigation/blob/main/packages/core/src/SpatialNavigation.ts) · [BAM’s API](https://github.com/bamlab/react-tv-space-navigation/blob/main/docs/api.md) · [Itar’s request and observation types](../packages/itar/src/api/types.ts)

## What to test in the beta

- **The return journey.** Try the two appearances of the same film on your target device. Move the opener to a new position, then repeat after removing it. Record the highlighted card and what Select opens. In Itar Cinema, Android uses `restoreFocusByKey` for the return. Apple and the browser example use `focusByKey` once the collection is ready. [Cinema’s route handling](../apps/probe/ott/src/Cinema.tsx) · [Integration guide](guides/integration.md)
- **Catalogue size and hardware.** Itar is a source beta you can pack locally. Its collection integration uses fixed extents, supports two levels and accepts up to 256 logical nodes per collection, including scopes. Run your realistic catalogue on the intended TV with its reader on and off. Chromecast HD testing found TalkBack focus jumps during loading. Physical VoiceOver checks on Apple TV remain open. BAM documents its own TalkBack integration as experimental. [Itar’s collection limits](guides/collections.md) · [Device status](devices/README.md) · [BAM accessibility notes](https://github.com/bamlab/react-tv-space-navigation/blob/main/docs/accessibility.md)
- **Responsiveness.** The native example compares eight mounted targets using platform controls, BAM 5.2.0 and Itar, and can briefly occupy JavaScript. Time the interval from a remote press to the first visible highlight on the same TV. The project has yet to publish comparable device measurements for latency or memory use. [Comparison screen](../apps/probe/ValidationScreen.tsx)
